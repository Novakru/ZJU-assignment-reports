Slide 1  Mind the Gap  (0:00–0:15)
Hi, I’m Jiahao Jiang. This CCS 2026 paper follows one simple question. When an Android agent sees one screen and acts on another, what can happen to the task the user authorized?

Sources
Qian et al., title and abstract. https://arxiv.org/pdf/2601.12349v3


Slide 2  One Tap, Two Screens  (0:15–0:55)
Start with the left phone in the authors’ Figure 1. The agent sees a text ready to send. In the blue thinking bubble it picks the SMS control. Follow the red labels to the right. A call takes the foreground before the input arrives. The same position now belongs to the answer button. The last phone shows the result of that input. The paper uses this everyday interruption to introduce action rebinding. On the next slide we can see where the two states diverge.

Sources
Qian et al., Figure 1, PDF p. 1. https://arxiv.org/pdf/2601.12349v3#page=1


Slide 3  Where the Two States Diverge  (0:55–1:40)
Read the two lanes together. At the first blue dot the agent observes the text screen. While it reasons from that observation, the foreground changes, as shown by the orange tick below. At the final dot Android delivers the pending input against the live screen. Visual atomicity is the assumption that the relevant state survives from observation through execution. In security terms, the observation is the check and input dispatch is the use. The figure gives us a TOCTOU race even when the initial screen recognition is accurate. The authors ask what happens when an app can influence the foreground state.

Sources
Qian et al., Sections 1 and 4, PDF pp. 1 and 4. https://arxiv.org/pdf/2601.12349v3#page=4


Slide 4  From an Interruption to a Security Test  (1:40–2:25)
Figure 2 gives the paper’s motivating case. On the left, the user asks the agent to write a note. On the right, the authors depict a completed purchase. The test asks whether an app influencing the foreground can cause an authorized agent to act in another app. The agent already has cross-app input authority. In the threat model, the app influencing the foreground does not need permission to make the purchase itself. That is how a change of receiving context can put an action outside the user’s request. The figure shows the requested task and illustrated outcome. The next slide shows how the authors measured outcomes beyond this one case.

Sources
Qian et al., Section 3 and Figure 2, PDF pp. 3–4. https://arxiv.org/pdf/2601.12349v3#page=4


Slide 5  What Did the Authors Measure?  (2:25–3:05)
The evaluation used six Android GUI agents and fifteen representative tasks. First, the authors recorded whether each specified outcome happened end to end. Every tested agent reached at least ten of the fifteen outcomes and two reached all fifteen. Next they examined why the outcome differed when several actions were needed. The middle line points us to acceptance and recovery as separate checks. The third line is a distinct verification-gate experiment, where the confirmation task stays fixed. We will read the last two comparisons from the original tables.

Sources
Qian et al., Sections 7.1–7.4, PDF Tables 2–4, pp. 7–9. https://arxiv.org/pdf/2601.12349v3#page=8


Slide 6  Reliable Single Taps, Uneven Recovery  (3:05–3:55)
The figure at the right is the paper’s reported single-action success in the tested setup across all six agents. Now look left at original Table 3, which covers five agents in the multi-step test. The middle column asks whether the agent followed the action expected by the displayed cue. The right column asks whether the agent returned to the original task app. All values in the middle are at least eighty-seven point five percent. Recovery falls to forty-five point seven percent for mobile-use and AutoGLM. A longer sequence needs prior progress to survive the switch and the agent to recover. The authors selected apps that retain UI state, so this column isolates the recovery stage. A verification dialog creates another decision point.

Slide 7  What Happens at the Confirmation?  (3:55–4:50)
Look at the two data columns in original Table 4. The authors test one confirmation task and compare a generic preceding context with IAS, their intent alignment strategy, where the preceding interface makes the dialog appear related to the task. Each row is an agent with ten trials in each column. In the middle column only one attempt was accepted. The right column sums to thirty-four. The totals on the right use all six agents, so the denominator is sixty in either condition. The IAS column spans three to ten acceptances out of ten across agents. The experiment suggests that a confirmation handled by the same model can inherit the context of its earlier observations.

Qian et al., Sections 6.3 and 7.4, PDF Table 4, p. 9. https://arxiv.org/pdf/2601.12349v3#page=9

Slide 8  Where the System Can Check the Target  (4:50–5:35)
Go back to the call. The Send action should be tied to the app, window, and version of the screen the agent used. My proposal is for the dispatcher to verify that context when delivering the input. If a call has taken over, drop the pending tap and observe again. For an irreversible operation, also ask the user to approve the specific action and target through a trusted flow. I would evaluate this on a mock interface with ordinary interruptions and measure wrong-target events together with completion, false cancellations, and delay. The paper’s security lesson is to verify which object actually receives the agent’s action.
