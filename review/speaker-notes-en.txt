Slide 1  Mind the Gap  (0:00–0:15)
Hi, I'm Jiahao Jiang. This CCS 2026 paper asks what happens when an Android agent acts on a screen that has changed since it looked.

Sources

Slide 2  When a Call Interrupts a Tap  (0:15–0:50)
Imagine asking the agent to add a note. Point to the orange circles. Both circles mark the same position on the phone. On the left, that position belongs to the add-note control. On the right, the call has taken over the screen. The paper calls the assumption that the observed screen still applies when the tap arrives visual atomicity. An ordinary call makes it easy to see how that assumption can fail.

Sources
Qian et al., Figure 1 and Section 4. https://arxiv.org/html/2601.12349v3


Slide 3  Who Authorizes and Who Acts?  (0:50–1:25)
Start with the user at the left. The user delegates a specific task. The GUI agent in the middle can read screens and send input across applications. Android delivers that input to the current target. In the paper’s threat model, the adversary controls one installed app with no dangerous permissions. The security issue is how the agent’s existing ability to act across apps can take an operation beyond the user’s task.

Sources
Qian et al., Section 3. https://arxiv.org/html/2601.12349v3


Slide 4  How a Tap Changes Targets  (1:25–2:25)
Read this timeline from left to right. The top row tracks the agent and the lower row tracks the foreground screen. At the first dot, the agent observes screen A. At the second dot it is still reasoning from that observation. The orange tick below marks a foreground change. By dispatch, screen B is in front. The tap still comes from the decision about A, but B can receive it. The authors call this action rebinding. The TOCTOU analogy is that the check uses the observed state and the use happens against the live state. Accurate recognition at the first dot only tells us what was there then.

Sources
Qian et al., Sections 4 and 5.1. https://arxiv.org/html/2601.12349v3


Slide 5  When a Task Takes More Than One Tap  (2:25–3:05)
The paper asks two follow-up questions. Read the blue row first. Can the agent resume after an interruption? A longer sequence depends on the app retaining state and the agent recovering. Then read the orange row. If the agent sees a confirmation, will it accept? The paper’s intent alignment strategy, or IAS, tests how task-related context influences that decision. We will look at recovery and confirmation in separate experiments.

Sources
Qian et al., Sections 6 and 7.3–7.4. https://arxiv.org/html/2601.12349v3


Slide 6  Single Actions and Multi-Step Recovery  (3:05–3:55)
Start with the number at the left. The paper reports one hundred percent single-action rebinding across the six agents in its tested setup. The bars at the right answer a different question from a separate test. They show how often each agent automatically recovered in a multi-step sequence. Three agents reached one hundred percent. Mobile-use and AutoGLM reached forty-five point seven percent. The study used apps that retain their UI state. Read the bars as recovery rates for that stage under those conditions.

Sources
Qian et al., Sections 7.3.1–7.3.2 and Table 1. https://arxiv.org/html/2601.12349v3


Slide 7  When the Agent Handles the Confirmation  (3:55–4:35)
Each bar pools six agents, with ten trials per agent per condition. The generic context produced one acceptance in sixty trials. When the context made the confirmation look relevant to the task, agents accepted thirty-four in sixty. This was one confirmation task and the individual agents differed. It shows why a confirmation handled by the same model can depend on what the model saw earlier.

Sources
Qian et al., Section 7.4 and Table 2. https://arxiv.org/html/2601.12349v3


Slide 8  The Check Belongs at Dispatch  (4:35–5:35)
Here is the design I propose in the report. Follow the two branches. A dispatcher compares the trusted application, window and UI state version with the planned action. When they still match, it can send the action to its bound target. When they have changed, it drops the old tap and observes again. Checking the app name alone can miss a change inside that app. For irreversible actions, I would also require independent approval of the action and target from the user. I would test this on a mock interface with ordinary UI changes and measure wrong-target input, task completion, false cancellations and delay.

Sources
Qian et al., Section 4. Controls and evaluation are proposed in the reading report.. https://arxiv.org/html/2601.12349v3
