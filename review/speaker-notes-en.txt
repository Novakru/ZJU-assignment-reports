Slide 1  Mind the Gap  (0:00–0:15)
Hi, I'm Jiahao Jiang. This CCS 2026 paper asks what happens when an Android agent acts on a screen that has changed since it looked.

Sources
Qian et al., Title and abstract. https://arxiv.org/html/2601.12349v3


Slide 2  A Valid Plan Can Reach the Wrong Screen  (0:15–0:50)
Imagine the agent prepares a tap, and an incoming call changes the foreground before the tap arrives. The earlier decision may have been entirely sensible. The operating system still has to answer a different question: which window and control should receive this input now? The authors call the assumption that the relevant screen stays valid until dispatch visual atomicity. It is an assumption about state over time.

Sources
Qian et al., Figure 1 and Section 4. https://arxiv.org/html/2601.12349v3


Slide 3  The Android Trust Boundary  (0:50–1:25)
The user authorizes a task. The agent can read the screen and dispatch input across apps. The paper assumes an installed app controlled by the adversary, with no dangerous Android permissions. A context mismatch can route the agent's action to an operation outside the task. The receiving app still runs under its own permissions. The problem is the unintended use of authority that the agent already has.

Sources
Qian et al., Section 3. https://arxiv.org/html/2601.12349v3


Slide 4  Observe, Reason, Act  (1:25–2:25)
Follow the three stages. At observation, the agent reads the interface and identifies a control in the current window. During reasoning, it decides what to do based on that observation. An ordinary event can change either the foreground window or a control within that window. At dispatch, the planned input may reach the current window even though it was selected from an earlier one. That mismatch is action rebinding. This is a time-of-check to time-of-use race: what was checked and what is used can differ. A model could identify the original control perfectly and still send an input that lands on the wrong target. The input layer needs a way to preserve the binding between the two.

Sources
Qian et al., Sections 4 and 5.1. https://arxiv.org/html/2601.12349v3


Slide 5  Why Extra Steps Change the Outcome  (2:25–3:05)
The paper distinguishes a single rebound action from a sequence of actions. A sequence needs the right state to persist and can depend on whether the agent resumes after a context change. The authors also test intent alignment, where earlier screen context can make a later confirmation appear relevant. For an agent, a dialog that seems to fit the task is evidence about plausibility. Approval also needs to come from the user and apply to the actual operation.

Sources
Qian et al., Sections 6 and 7.3–7.4. https://arxiv.org/html/2601.12349v3


Slide 6  Single Actions and Multi-Step Recovery  (3:05–3:55)
The authors report one hundred percent success for single-action rebinding in their tests across six open-source Android agents. Table 1 measures recovery in a separate multi-step experiment. Among the five agents in that table, the recovery rate ranges from 45.7 percent to one hundred percent. Recovery is just one stage of a chain. The study selected apps that preserve their screen state, so those percentages are specific to the setup. The results show the problem can appear in several implementations. To estimate its frequency in everyday use, we would need a wider sample of devices, apps, and agent settings.

Sources
Qian et al., Sections 7.3.1–7.3.2 and Table 1. https://arxiv.org/html/2601.12349v3


Slide 7  Acceptance at a Confirmation Gate  (3:55–4:35)
For the confirmation experiment, the authors ran ten trials per condition for each of six agents. Summing Table 2, agents accepted one out of sixty confirmations in the generic condition and thirty-four out of sixty in the intent-aligned condition. These are repeated trials for one confirmation task, and performance varies by agent. The change suggests that confirmation by the same model is sensitive to the context it has received.

Sources
Qian et al., Section 7.4 and Table 2. https://arxiv.org/html/2601.12349v3


Slide 8  Controls at Input Dispatch  (4:35–5:35)
My proposal is to bind each planned action to trusted identifiers for the app and window and to a state version. The dispatcher should validate that binding when it sends the event. On mismatch, discard the pending action, observe again, and then decide whether to proceed. Checking the app name alone misses changes within an app. A sensitive operation can also require an independent user approval tied to the exact action and destination. These are design proposals. In a mock GUI, I would measure wrong-context dispatches alongside task completion, false cancellations, and latency.

Sources
Qian et al., Section 4. Controls and evaluation are proposed in the reading report.. https://arxiv.org/html/2601.12349v3
